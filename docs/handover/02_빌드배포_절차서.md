# 머물전남 빌드·배포 절차서

개발자용 문서예요. 이 저장소를 받은 사람이 로컬에서 실행하고, 검사하고, 배포하고, 문제가 생기면 되돌리는 방법을 적었어요.
작성 기준은 2026-11-10, `main` 브랜치예요. `main`은 라이브(https://jeonnam-trip.web.app)와 같은 코드예요.

이 문서에는 키·시크릿·비밀번호 값을 적지 않았어요. 환경변수는 이름과 넣는 위치만 적었어요.

## 3. 로컬 실행

### 3-1. 설치

```bash
npm ci
npm --prefix functions ci
npx playwright install chromium   # 스모크 테스트를 돌릴 때만
```

### 3-2. 에뮬레이터로 실행 (기본)

기본 설정에서는 `npm run dev`가 로컬 에뮬레이터에 붙어요. 운영 데이터를 건드리지 않아요.

```bash
npm --prefix functions run build   # 함수 에뮬레이터는 functions/lib를 읽어요
npm run emulators                  # 터미널 1: auth·functions·firestore·storage + UI
npm run seed:test                  # 터미널 2: 테스트 계정 3개 생성
npm run seed:sample                # [샘플] 축제·장소·코스 + 테스트 관리자 등록
npm run dev                        # http://localhost:5173
```

| 에뮬레이터 | 포트 |
|---|---|
| Auth | 9099 |
| Functions | 5001 |
| Firestore | 8080 |
| Storage | 9199 |
| Emulator UI | 활성 (주소는 실행 로그에 나와요) |

에뮬레이터 모드에서 Vite 개발 서버는 `/api/auth/kakao`를 `127.0.0.1:5001/jeonnam-trip/asia-northeast3/authKakao`로, 나머지 `/api`를 같은 곳의 `api` 함수로 넘겨요(`vite.config.ts`).

함수 에뮬레이터에서 시크릿(`NAVER_MAP_CLIENT_SECRET`, `KAKAO_CLIENT_SECRET`)이 필요하면 `functions/.secret.local`에 넣으세요. 이 파일은 `functions/.gitignore`에 들어 있어요. 이 파일이 없으면 Secret Manager 접근 권한이 있는 계정으로 `firebase login`해야 해요. 둘 다 없으면 로컬에서 경로 계산(`api`)과 카카오 로그인(`authKakao`)이 실패해요. 값은 담당자에게 따로 받아요.

### 3-3. 운영 데이터를 읽으며 실행

`.env.local`에 `VITE_USE_EMULATORS=false`를 두면 에뮬레이터 대신 운영 Firebase에 붙고, `/api`는 https://jeonnam-trip.web.app 으로 넘어가요. 운영 데이터를 직접 읽고 쓰게 되니 조심하세요.

### 3-4. 로컬에서 안 되는 것

| 기능 | 상태 |
|---|---|
| 카카오 로그인 | 함수 코드의 허용 목록에는 `http://localhost:5173/auth/kakao/callback`이 있지만, 카카오 콘솔에는 운영 주소만 등록돼 있다고 `vite.config.ts` 주석에 적혀 있어요. 로컬에서는 끝까지 되지 않아요. |
| 네이버 지도 | NCP 콘솔 Web 서비스 URL에 등록된 주소에서만 떠요. 이 문서 부록 D S6에는 `http://localhost:5173`이 미등록으로 남아 있어요. 이전 담당자는 2026-10-26부터 localhost에서도 떴다고 확인했지만, 저장소에 남은 근거는 없어요. 처음 실행할 때 NCP 콘솔 → Maps → Application → Web 서비스 URL에 `http://localhost:5173`이 있는지 확인하고, 결과에 맞춰 부록 D의 S6도 고쳐 주세요. 지도는 배포 후 라이브에서 확인하는 것이 가장 확실해요. |
| PR 미리보기 채널의 지도·로그인 | 이 문서 부록 D F6(Firebase Auth 승인 도메인에 미리보기 도메인 추가)이 미완료로 남아 있어요. 미리보기에서 로그인·지도를 확인하려면 Firebase 콘솔 승인 도메인과 NCP 콘솔 Web 서비스 URL에 미리보기 도메인이 있는지 먼저 확인해 주세요. |

### 3-5. 테스트 로그인

`import.meta.env.DEV`이고 `VITE_USE_EMULATORS`가 참일 때만 테스트 로그인이 켜져요(`src/lib/test-auth.ts`). 프로덕션 빌드에서는 동작하지 않아요. 계정 규약은 이 문서 부록 A를 보세요.

## 4. 환경변수 전체 표

### 4-1. 웹 앱 (VITE_)

앱은 `src/lib/env.ts` 한 곳에서 zod로 검증해요. 필수 값이 빠지면 앱이 시작할 때 '환경변수 누락/오류' 에러를 던져요. `VITE_` 값은 번들에 평문으로 들어가므로 시크릿을 넣으면 안 돼요.

| 이름 | 필수 | 용도 | 로컬 | GitHub Actions |
|---|---|---|---|---|
| `VITE_FIREBASE_API_KEY` | 필수 | Firebase 웹 설정 | 루트 `.env` | Variables |
| `VITE_FIREBASE_AUTH_DOMAIN` | 필수 | Firebase 웹 설정 | 루트 `.env` | Variables |
| `VITE_FIREBASE_PROJECT_ID` | 필수 | Firebase 웹 설정 | 루트 `.env` | Variables |
| `VITE_FIREBASE_STORAGE_BUCKET` | 필수 | Firebase 웹 설정 | 루트 `.env` | Variables |
| `VITE_FIREBASE_MESSAGING_SENDER_ID` | 필수 | Firebase 웹 설정 | 루트 `.env` | Variables |
| `VITE_FIREBASE_APP_ID` | 필수 | Firebase 웹 설정 | 루트 `.env` | Variables |
| `VITE_NAVER_MAP_CLIENT_ID` | 필수 | 네이버 지도 JS v3 로드(`ncpKeyId`). 서비스 URL로 제한되는 공개 값 | 루트 `.env` | Variables |
| `VITE_KAKAO_JS_KEY` | 필수 | 카카오 JS SDK 초기화 | 루트 `.env` | Variables |
| `VITE_SENTRY_DSN` | 선택 | 없으면 Sentry 비활성. 지금은 Sentry 패키지·초기화 코드가 없어서 쓰이지 않아요 | 넣지 않아도 돼요 | 워크플로우 env에는 있지만 Variables에는 미등록 |
| `VITE_USE_EMULATORS` | 선택 | 기본 `true`. `false`일 때만 에뮬레이터를 끄고 운영에 붙어요 | 루트 `.env` 또는 `.env.local` | 프로덕션 빌드는 DEV가 아니어서 무시돼요 |

파일 정책은 아래와 같아요.

| 파일 | git | 내용 |
|---|---|---|
| `.env.example`, `functions/.env.example` | 커밋됨 | 변수 이름과 설명만 있는 예시. 복사해서 `.env`, `functions/.env`를 만들어요 |
| `.env`, `functions/.env` | 제외 | 실제 값. 레포에 올리지 않아요 |
| `.env.local`, `.env.*.local` | 제외 | 개인 로컬 설정. 지금은 `VITE_USE_EMULATORS`만 둬요 |
| `.secrets/` | 제외 | 로컬 비밀 파일 보관용 |

주의: `.env`는 레포에 없어서 Actions 배포 빌드는 저장소 Variables 값만 써요. Variables에 빠진 이름이 있으면 그 값이 비어 빌드되고, 사이트가 환경변수 오류로 흰 화면이 돼요. 새 `VITE_` 변수를 추가하면 `src/lib/env.ts`, `.env.example`, `firebase-hosting-deploy.yml`의 env 목록, 저장소 Variables 네 곳을 함께 고쳐요.

### 4-3. Cloud Functions

| 이름 | 종류 | 쓰는 함수 | 넣는 곳 |
|---|---|---|---|
| `NAVER_MAP_CLIENT_ID` | `defineString` (공개 값) | `api` | `functions/.env` (예시 파일 복사 후 채움) |

시크릿은 Firebase CLI로 등록하고 확인해요. README의 Functions 절과 같은 명령이에요. 값은 실행하면 프롬프트로 입력해요.

```bash
firebase functions:secrets:set NAVER_MAP_CLIENT_SECRET --project jeonnam-trip
firebase functions:secrets:set KAKAO_CLIENT_SECRET --project jeonnam-trip
gcloud secrets versions list KAKAO_CLIENT_SECRET --project=jeonnam-trip
```

시크릿 값을 바꾼 뒤에는 그 시크릿을 쓰는 함수를 다시 배포해야 새 값이 적용돼요.

## 5. 검사 명령

| 명령 | 하는 일 |
|---|---|
| `npm run lint` | ESLint 9 (typescript-eslint strictTypeChecked, react-hooks, jsx-a11y). `functions/`, `e2e/`는 대상이 아니에요 |
| `npm run typecheck` | `tsc -b --noEmit` |
| `npm run test` | Vitest 감시 모드. 한 번만 돌리려면 `npm run test -- --run` |
| `npm run build` | `tsc -b && vite build`. 직전에 `prebuild`가 웹 에셋 검사를 경고 모드로 돌려요 |
| `npm run check:web-assets` | 파비콘·앱 아이콘·매니페스트·OG 이미지·robots를 엄격 모드로 검사. 실패하면 exit 1 |
| `npm run smoke` | Playwright로 `e2e/`를 실행. 빌드 후 `vite preview`(4173)를 띄워요. 로컬에서는 `.env` 값으로 빌드해 운영 데이터를 읽어요(쓰기는 없어요). 운영과 떼려면 `react-ci.yml` smoke 잡처럼 가짜 `VITE_` 값을 env로 주고 돌리세요 |
| `npx prettier --check .` | 서식 검사. CI에서 돌아요 |
| `npm --prefix functions test` | 함수 단위 테스트(`node --test`, directions·kakao-auth) |
| `npm --prefix functions run build` | 함수 TypeScript 빌드(`functions/lib`) |

푸시 전에는 아래를 돌리세요. CI(`react-ci.yml`)와 같은 순서예요.

```bash
npx prettier --check .
npm run lint
npm run typecheck
npm run test -- --run --coverage
npm run build
npm run check:web-assets
```

새 공개 라우트를 추가했다면 `e2e/smoke.spec.ts`의 `ROUTES`에도 등록하세요.

## 6. 배포

배포 대상은 세 가지로 나뉘어요. GitHub Actions는 Hosting만 배포해요.

| 대상 | 자동 배포 | 수동 명령 |
|---|---|---|
| Hosting (웹 앱) | main 푸시 → live, main 대상 PR → 미리보기 | `firebase deploy --only hosting --project jeonnam-trip` |
| Firestore·Storage 규칙, 인덱스 | 없음 | `firebase deploy --only firestore:rules,firestore:indexes,storage --project jeonnam-trip` |
| Cloud Functions | 없음 | `firebase deploy --only functions --project jeonnam-trip` |

### 6-1. GitHub Actions 자동 배포

워크플로우는 두 개예요.

| 파일 | 실행 조건 | 하는 일 |
|---|---|---|
| `.github/workflows/react-ci.yml` | `main`·`dev` 브랜치 푸시와 PR | `npm ci` → prettier 검사 → lint → typecheck → test(커버리지) → build → `npm audit --audit-level=high`(실패해도 계속). 별도 잡으로 Playwright 스모크. 배포는 하지 않아요 |
| `.github/workflows/firebase-hosting-deploy.yml` | `main` 대상 PR, `main` 푸시 | `npm ci` → `npm run build`(`WEB_ASSETS_STRICT=1`) → 배포 |

배포 워크플로우 동작은 아래와 같아요.

| 이벤트 | 결과 |
|---|---|
| `main` 대상 PR (같은 저장소 브랜치) | 미리보기 채널에 배포, 7일 뒤 만료. PR 코멘트에 URL이 달려요 |
| 포크에서 온 PR | 시크릿이 없어서 건너뛰어요 |
| `main` 푸시 (PR 머지 포함) | live 채널에 배포 |

`main`에 머지하는 순간 라이브가 바뀌어요. 머지 전에 미리보기 채널에서 화면을 확인하세요. CI의 스모크 잡은 가짜 Firebase 값(`VITE_FIREBASE_PROJECT_ID=smoke`, `VITE_USE_EMULATORS=false`)으로 빌드해서 운영 Firebase를 건드리지 않아요.

### 6-2. 수동 Hosting 배포

첫 라이브 배포(2026-10-16)는 CLI로 했어요. 급하게 고쳐야 하거나 Actions가 막혔을 때 이 방법을 써요.

```bash
npm ci
npm run check:web-assets
npm run build
firebase deploy --only hosting --project jeonnam-trip
```

로컬 빌드는 루트 `.env`와 `.env.local`을 읽어요. 에뮬레이터 연결은 `import.meta.env.DEV`일 때만 켜지므로, `VITE_USE_EMULATORS` 값과 상관없이 `vite build` 결과물은 운영 Firebase에 붙어요.

미리보기 채널만 따로 만들 수도 있어요.

```bash
firebase hosting:channel:deploy <채널이름> --expires 7d --project jeonnam-trip
```

터미널에서 직접 배포할 때는 배포 전에 `npm run check:web-assets`를 먼저 돌려 파비콘·앱 아이콘·OG 이미지가 빠지지 않았는지 확인하세요.

### 6-3. Functions·규칙 배포

Functions 배포 전 준비예요. `firebase.json`의 predeploy가 `npm --prefix functions run build`를 돌리므로 `functions/node_modules`가 있어야 해요.

```bash
npm --prefix functions ci
npm --prefix functions test
firebase deploy --only functions --project jeonnam-trip
```

함수 하나만 배포할 수도 있어요.

```bash
firebase deploy --only functions:api --project jeonnam-trip
firebase deploy --only functions:authKakao --project jeonnam-trip
firebase functions:list --project jeonnam-trip
```

Functions 배포 시 주의할 점이에요.

| 주의 | 내용 |
|---|---|
| 시크릿 먼저 | `NAVER_MAP_CLIENT_SECRET`, `KAKAO_CLIENT_SECRET`이 Secret Manager에 있어야 배포가 돼요. 두 함수를 나눠 둔 이유는 카카오 시크릿이 없어도 경로 API 배포가 막히지 않게 하려는 거예요 |
| 실행 계정 | `authKakao`는 Admin SDK 서비스 계정으로 실행돼요. 배포하는 계정에 그 서비스 계정을 쓸 권한이 있어야 해요 |
| 리전 | 두 함수 모두 asia-northeast3예요. 리전을 바꾸면 `firebase.json` rewrite와 `vite.config.ts` 프록시 주소도 같이 바꿔야 해요 |
| 카카오 redirect URI | 허용 목록(`functions/src/kakao-auth.ts`)과 카카오 콘솔 등록값, `paths.kakaoCallback`이 모두 같아야 해요. 다르면 KOE303이 나요 |
| 외부 도메인 | 새 외부 스크립트·API 도메인을 쓰면 `firebase.json`의 CSP 헤더도 고치고 Hosting을 다시 배포하세요 |

규칙·인덱스 배포예요.

```bash
firebase deploy --only firestore:rules,storage --project jeonnam-trip
firebase deploy --only firestore:indexes --project jeonnam-trip
```

Storage는 `storage:rules`가 아니라 `storage`로 적어요. `firebase.json`의 storage에는 deploy target이 없어서, `storage:rules`라고 쓰면 CLI가 `rules`를 target 이름으로 읽고 'Could not find rules for the following storage targets' 에러로 멈춰요. `firebase-hosting-deploy.yml` 71행 주석에도 같은 오타(`storage:rules`)가 있으니 그대로 따라 하지 마세요.

규칙을 바꾸는 커밋은 Hosting 배포와 따로 움직이므로, 클라이언트 코드가 라이브에 올라가는 시점과 규칙 배포 시점을 맞추세요. 새 쿼리가 새 규칙을 필요로 하면 규칙을 먼저 배포하는 편이 안전해요.

### 6-4. Storage CORS

버킷 CORS는 `cors.json`에 있어요(허용 origin: localhost:5173, jeonnam-trip.web.app, jeonnam-trip.firebaseapp.com, 메서드 GET·HEAD). 이 문서 부록 D에는 적용(F7)이 미완료로 남아 있어요.

```bash
gcloud storage buckets update gs://jeonnam-trip.firebasestorage.app --cors-file=cors.json
```

## 8. 에뮬레이터와 시드

| 명령 | 하는 일 | 운영 접속 |
|---|---|---|
| `npm run emulators` | `firebase emulators:start --project jeonnam-trip` | 없음 |
| `npm run seed:test` | Auth 에뮬레이터에 테스트 계정 3개(관리자 1, 일반 2) 생성 | 없음 |
| `npm run seed:sample` | Firestore 에뮬레이터에 [샘플] 축제·장소·크리에이터 코스를 넣고 테스트 관리자 계정을 `admins`에 등록 | 없음 |

순서는 `emulators` → `seed:test` → `seed:sample`이에요. `seed:sample`은 테스트 관리자 계정이 없으면 관리자 등록을 건너뛰어요. 샘플 데이터는 모두 가상이고, 이름에 `[샘플]`이 붙어 있어요. 테스트 계정의 비밀번호와 인증번호 규약은 이 문서 부록 A에 있어요.

이 문서 부록 D F4(에뮬레이터 실행·로컬 연결 확인)는 아직 미완료로 남아 있어요. 처음 실행할 때 위 순서가 그대로 되는지 한 번 확인하고 체크리스트를 갱신하세요.

운영 데이터 스크립트는 따로 있어요. 모두 운영 Firestore·Storage에 직접 쓰고 보안 규칙을 거치지 않아요. 기본은 dry-run이고 `--write`를 붙여야 반영돼요.

| 스크립트 | 하는 일 | 실행 예 (각 파일 첫 주석 기준) |
|---|---|---|
| `scripts/crawl-namdo-festivals.mjs` | 남도여행길잡이 축제 수집 → `festivals`, Storage 사진 | `node scripts/crawl-namdo-festivals.mjs --year 2026 --out <파일.json>`. `--year`를 빼면 올해예요. 반영은 `--write`를 붙이고 `GCP_TOKEN`(지오코딩까지 하려면 `NCP_ID`·`NCP_SECRET`)을 줘요 |
| `scripts/crawl-namdo-places.mjs` | 장소·추천 코스 수집 → `places`, `creatorCourses`, Storage 사진 | `node scripts/crawl-namdo-places.mjs --out <파일.json>`. `--out`은 꼭 붙이세요. 빠지면 첫 인자를 파일 이름으로 써요. 반영은 `GCP_TOKEN`을 주고 `--write --out <파일.json>` |
| `scripts/fill-festival-photos.mjs` | `scripts/data/festival-photos.json` 매니페스트로 축제 사진 채우기 | `node scripts/fill-festival-photos.mjs`. dry-run에서도 운영 Firestore를 읽어서 `GCP_TOKEN`이 꼭 있어야 해요. 반영은 `--write`, 이미 사진이 있는 축제까지 바꾸려면 `--write --force` |
| `scripts/apply-translations.mjs` | `scripts/data/*-i18n.json`을 각 문서의 `i18n` 필드에 반영 | `node scripts/apply-translations.mjs`(건수만 세요), 반영은 `--write` |

```bash
export GCP_TOKEN="$(gcloud auth print-access-token)"
node scripts/apply-translations.mjs           # dry-run
node scripts/apply-translations.mjs --write   # 반영
```

`GCP_TOKEN`은 발급하고 약 1시간 뒤 만료돼요. 오래 걸리는 수집 중에 인증 오류가 나면 토큰을 다시 받아서 돌리세요.

`crawl-namdo-*.mjs --write`는 문서를 통째로 덮어써서 `i18n` 필드가 지워져요. 수집을 다시 돌렸다면 `apply-translations.mjs --write`도 다시 돌리세요.

## 9. 롤백

### 9-1. Hosting 이전 버전으로 되돌리기

가장 빠른 방법은 Firebase 콘솔이에요. Hosting → 사이트 `jeonnam-trip` → 출시 기록에서 되돌릴 버전을 골라 롤백하세요.

CLI로도 할 수 있어요. 버전 ID는 콘솔 출시 기록에서 확인해요.

```bash
firebase hosting:clone jeonnam-trip@<버전ID> jeonnam-trip:live --project jeonnam-trip
```

미리보기 채널에서 확인한 빌드를 그대로 live로 올릴 때도 같은 명령을 써요.

```bash
firebase hosting:clone jeonnam-trip:<채널이름> jeonnam-trip:live --project jeonnam-trip
```

Hosting 롤백은 웹 앱 파일만 되돌려요. Functions와 규칙은 그대로예요. 또 다음 `main` 푸시가 다시 배포하므로, 롤백한 뒤에는 바로 아래 git revert로 `main`도 맞춰 두세요.

### 9-2. git revert

`main`의 문제 커밋을 되돌리는 커밋을 만들어 PR로 머지해요. 머지되면 Actions가 되돌린 상태를 live에 배포해요.

```bash
git switch main
git pull
git switch -c fix/revert-<요약>
git revert <커밋해시>            # 머지 커밋이면 git revert -m 1 <커밋해시>
git push -u origin fix/revert-<요약>
gh pr create --base main
```

### 9-3. Functions·규칙 되돌리기

| 대상 | 방법 |
|---|---|
| Functions | 이전 코드로 revert한 뒤 `firebase deploy --only functions --project jeonnam-trip`로 다시 배포해요 |
| Firestore·Storage 규칙 | Firebase 콘솔 규칙 탭의 이전 버전으로 되돌리거나, revert한 규칙 파일을 다시 배포해요 |
| 시크릿 | Secret Manager에서 이전 버전을 다시 활성화하거나 새 값을 등록한 뒤 함수를 다시 배포해요 |

## 10. 브랜치·PR·커밋 규칙

### 10-1. 브랜치 현황

이 레포는 `main` 브랜치 하나로 시작해요. `main`이 라이브 기준이에요. `main`에 푸시(머지)하면 Actions가 live에 배포하고, PR을 열면 미리보기 채널에 배포돼요.

### 10-2. 브랜치·PR 규칙

| 규칙 | 내용 |
|---|---|
| 기준 브랜치 | `main` |
| 작업 방식 | `main`에서 새 브랜치를 만들고 PR로 머지해요. `main`에 직접 푸시하면 바로 라이브에 배포되니 피하세요 |
| PR 확인 | CI(React CI) 통과, 미리보기 채널 URL에서 화면 확인 |
| PR 본문 | 문제 / 변경 / 검증 순서로 쓰고, 사용자 관점 증상을 먼저 적어요 |
| 규칙·함수 변경 | PR 본문에 수동 배포가 필요하다고 적고, 머지 후 6-3 명령으로 배포해요 |

### 10-3. 커밋 규칙

형식은 아래와 같아요.

```text
<type>(<scope>): <설명>
```

| 항목 | 규칙 |
|---|---|
| type | `feat`, `fix`, `refactor`, `test`, `docs`, `style`, `perf` |
| scope | 기능 폴더 이름(예: `planner`, `account`, `library`, `brand`) |
| 한 커밋 | 로직, 리팩터, 서식 중 하나만 담아요 |
| 규칙 파일 | `firestore.rules`, `storage.rules`는 관련 코드와 같은 커밋에 넣어요 |

최근 커밋 예시예요.

```text
feat(planner): show names on search markers, open a card on tap, and pick which day to add to
feat(library): show the place intro, today's hours, and a short address on saved cards
fix(planner): give the route map a real height inside tabs, move add-a-night next to the day tab, and show only warnings
```

지금까지 커밋 제목은 영어 설명으로 써 왔어요. 한국어로 바꿀지는 넘겨받은 뒤 팀에서 정하세요.

### 부록 A. 테스트 계정 규약

> QA·개발·심사 리뷰어가 쓰는 테스트 로그인의 **단일 출처**. 코드는 `src/lib/test-auth.ts`가 소유.

#### 요약 (개발/에뮬레이터 전용)

| 종류 | 값 | 비고 |
|------|-----|------|
| 전화번호 | `01011111111` ~ `01099999999` (010 + 8자리 전체) | 인증번호 **123456** |
| 이메일 도메인 | `*@test.local` | 비번 **test123456!** (없으면 자동 생성) |
| 시드 계정 | `admin@test.local` / `user@test.local` / `user2@test.local` | 비번 동일, `npm run seed:test`로 생성 |

#### ⚠️ 보안 — 프로덕션 하드 차단

`src/lib/test-auth.ts`는 **`import.meta.env.DEV` AND `VITE_USE_EMULATORS`** 를 둘 다 만족할 때만
동작한다. 프로덕션 빌드(DEV=false)에서는 모든 함수가 즉시 throw한다. **이 이중 가드를 절대 완화하지
말 것** — 고정 OTP(123456)가 실서비스에서 통하면 아무 번호로나 로그인되는 계정 탈취 백도어가 된다.

- 전화 범위 전체를 123456으로 통하게 하는 건 **앱 레벨 바이패스**로만 가능하다. Firebase 콘솔의
  "테스트 전화번호"는 프로젝트당 **10개 상한**이라 8,900만 개 범위를 콘솔로는 못 넣는다.
- 합성 전화 계정은 이메일/비번 유저다 — `auth.currentUser.phoneNumber`는 null, `email`이 채워진다.
  화면이 전화번호를 읽어야 하면 Firestore 프로필에 저장해 쓴다.

#### 로그인 UI 배선 (프로젝트에서)

로그인 핸들러에서 테스트 입력이면 실 인증 대신 test-auth로 분기한다:

```tsx
import { isTestPhone, testPhoneSignIn, isTestEmail, testEmailSignIn } from "@/lib/test-auth";

async function onSubmitPhone(phone: string, code: string) {
  if (isTestPhone(phone)) {
    await testPhoneSignIn(phone, code); // dev+에뮬레이터에서만 true
    return;
  }
  // ...실제 signInWithPhoneNumber 흐름
}

async function onSubmitEmail(email: string, password: string) {
  if (isTestEmail(email)) {
    await testEmailSignIn(email, password);
    return;
  }
  // ...실제 signInWithEmailAndPassword 흐름
}
```

`isTestPhone`/`isTestEmail`은 프로덕션에서 항상 false라 실 인증 흐름만 남는다.

#### 프로덕션 QA가 필요할 때 (앱스토어 심사 등)

실 프로덕션에서 리뷰어가 로그인해야 하면 (dev 바이패스는 프로덕션에서 안 됨):
1. Firebase 콘솔 → Authentication → Sign-in method → 전화 → "테스트용 전화번호"에 **≤10개** 등록
   (번호 + 고정 코드 쌍). 이건 실 SMS 없이 프로덕션에서도 통한다.
2. 또는 이메일/비번 심사 계정 1개를 실 프로젝트에 만들어 리뷰 노트에 제공.

### 부록 B. Storage·Functions CORS

> React+Firebase 웹앱에서 CORS가 막히는 4곳과 각 해법의 **단일 출처**. 원칙: **가능하면 CORS를
> 마주치지 않게 설계**(같은 오리진)하고, 불가피한 Storage 다운로드만 버킷 CORS로 연다.

#### 어디서 CORS가 나오나 — 결정 트리

| 상황 | 오리진 | 해법 |
|------|--------|------|
| SPA가 자기 정적 파일 로드 | 같은 오리진 | CORS 없음 |
| SPA → Cloud Function 호출 | 다름(cloudfunctions.net) | **① onCall(자동) 또는 ② Hosting `/api` rewrite(같은 오리진화)** — 아래 2·3 |
| SPA → Storage 파일 `fetch`/canvas | 다름(firebasestorage.app) | **③ 버킷 CORS(cors.json)** — 아래 1 |
| SPA → 외부 서드파티 API | 다름 | 브라우저 직접 호출 금지 → **Cloud Function 프록시** 경유 |
| 로컬 dev에서 위 호출 | localhost | **④ Vite dev proxy** — 아래 4 |

**핵심**: 앱↔Functions는 CORS를 "여는" 게 아니라 **같은 오리진으로 만들어 피하는** 게 정석
(Hosting rewrite). Storage 다운로드만 진짜로 버킷 CORS가 필요하다.

---

#### 1. Firebase Storage 버킷 CORS

`getDownloadURL()` 결과를 `<img src>`로 쓰는 것만이면 대개 불필요하지만, **`fetch()`로 받거나
`<img crossorigin>`/canvas로 읽으면** 버킷 CORS가 필요하다. 설정은 `templates/firebase/cors.json`
(이 프로젝트 루트에 복사됨)을 버킷에 적용:

```bash
### 현재 권장 (gcloud storage) — 버킷명은 프로젝트 실제 값 (신규=PROJECT.firebasestorage.app, 레거시=PROJECT.appspot.com)
gcloud storage buckets update gs://[PROJECT_ID].firebasestorage.app --cors-file=cors.json

### 레거시 등가 (gsutil — 여전히 동작하나 gcloud storage가 권장)
gsutil cors set cors.json gs://[PROJECT_ID].firebasestorage.app
```

- **버킷명**: `.env`의 `VITE_FIREBASE_STORAGE_BUCKET` 값 그대로 (하드코딩 접미사 금지 — 2024-10부터
  신규 프로젝트는 `firebasestorage.app`, 레거시는 `appspot.com`).
- **cors.json은 최상위 배열**(`{"cors":[...]}` 래퍼 없음) — gcloud/gsutil CLI 공통.
- **origin에 `*` 금지**(프로덕션) — 아무 사이트나 우리 스토리지를 읽게 된다. 실제 도메인(localhost dev +
  web.app + 커스텀 도메인)만 나열. cors.json의 `[PROJECT_ID]`·`[PRODUCTION_DOMAIN]`을 실값으로 치환.
- 적용 후 브라우저 캐시(`maxAgeSeconds`) 때문에 반영이 늦을 수 있음 — 하드리로드로 확인.

---

#### 2. Cloud Functions CORS (firebase-functions v2)

- **Callable(`onCall`)은 CORS 자동 처리** — 브라우저 SDK(`httpsCallable`)가 관리. **앱→함수 호출은
  가능하면 onCall을 기본으로** 쓴다 (CORS 작업 0).
- **HTTP(`onRequest`)는 v2 내장 `cors` 옵션** 사용 — `cors` npm 패키지 불필요:
  ```js
  const { onRequest } = require("firebase-functions/v2/https");
  // 전체 허용
  exports.api = onRequest({ cors: true }, (req, res) => { res.send("ok"); });
  // 특정 오리진만 (문자열/정규식 배열)
  exports.api = onRequest({ cors: ["https://[PROJECT_ID].web.app", /\.[도메인]$/] }, handler);
  ```
  `cors` 없으면 헤더가 안 붙어 브라우저 호출이 차단된다. preflight(OPTIONS)도 이 옵션이 자동 처리.

---

#### 3. Hosting rewrite로 CORS 회피 (권장 기본 패턴)

SPA가 **같은 오리진 경로(`/api/**`)** 를 호출하면 Hosting이 함수로 프록시 → **CORS 자체가 없음**.
`firebase.json` (templates/firebase/firebase.json.example 참조):

```json
"rewrites": [
  { "source": "/api/**", "function": { "functionId": "api", "region": "asia-northeast3", "pinTag": true } },
  { "source": "**", "destination": "/index.html" }
]
```
- v2 함수는 **객체 형식**(`functionId`+`region`) 사용. `region`은 함수 배포 리전과 일치시켜 명시.
- `/api/**` rewrite를 **SPA catch-all(`**`)보다 먼저** 둔다 (순서 중요).
- 앱에서는 `fetch("/api/…")`로 호출 → 오리진이 같아 CORS·preflight 없음. **함수를 쓰면 이 방식이 1순위.**

---

#### 4. Vite dev proxy (로컬 개발)

로컬에서 `/api` 호출을 에뮬레이터 함수로 프록시해 dev에서도 CORS를 피한다. `vite.config.ts`:

```ts
server: {
  proxy: {
    "/api": {
      target: "http://127.0.0.1:5001/[PROJECT_ID]/asia-northeast3",
      changeOrigin: true,
      rewrite: (p) => p.replace(/^\/api/, ""),
    },
  },
},
```
`target`을 에뮬레이터 함수 엔드포인트로, `rewrite`로 `/api` 접두사를 제거해 최종 경로가 함수에 닿게 한다.

---

#### App Check + CORS (App Check 켤 때)

App Check 토큰은 커스텀 헤더 `X-Firebase-AppCheck`로 전송되고, **커스텀 헤더는 브라우저 preflight를
유발**한다. callable은 자동 처리되지만, **onRequest는 위 `cors` 옵션(또는 Hosting rewrite로 같은
오리진)** 이어야 preflight를 통과한다. App Check 시행(enforcement)과 CORS는 별개라 둘 다 설정 필요.

#### 참고 (2026)
- gsutil → **gcloud storage**가 현재 GCS 권장 (Firebase 문서는 아직 gsutil 표기 — 뒤처진 것).
- 기본 버킷 접미사 `firebasestorage.app`(2024-10~), 신규 기본 버킷은 Blaze 필요.
- Functions 2세대 = "Cloud Run functions" 개명, `cloudfunctions.net`·`run.app` URL 둘 다 발급(동일 동작).
  Hosting rewrite를 쓰면 어느 URL에도 의존하지 않아 가장 견고.

### 부록 C. 데이터 모델

> 인계 산출물 "데이터 구조·설정 설명"의 기준 문서. 타입 단일 출처는 `src/shared/domain/`, 규칙은 `firestore.rules`·`storage.rules`.

#### Firestore 컬렉션

| 컬렉션 | 문서 | 읽기 | 쓰기 |
|---|---|---|---|
| `places/{id}` | `Place` | `status == "published"`면 누구나, 관리자는 전부 | 관리자 |
| `festivals/{id}` | `Festival` | 위와 같음 | 관리자 |
| `creatorCourses/{id}` | `CreatorCourse` | 위와 같음 | 관리자 |
| `contentDrafts/{kind}__{id}` | 공개 중 콘텐츠의 수정 초안 | 관리자 | 관리자 |
| `admins/{uid}` | 관리자 명단 | 본인 | 클라이언트 불가 (콘솔·CLI) |
| `trips/{id}` | `Trip` (`ownerUid`, `version`) | 소유자 | 소유자. 생성 `version == 1`, 수정은 `version + 1`만 |
| `shares/{id}` | `SharedTrip` 공개 사본 | `active`면 링크를 아는 누구나 단건 조회, 목록은 소유자 | 소유자 (자기 코스로만 생성) |
| `users/{uid}/savedPlaces/{id}` | `SavedPlace` | 본인 | 본인 |
| `users/{uid}/customPlaces/{id}` | `CustomPlace` | 본인 | 본인 |
| `users/{uid}/snsLinks/{id}` | `SnsLink` | 본인 | 본인 |

- 운영 콘텐츠 목록 쿼리는 반드시 `where("status", "==", "published")`를 포함한다 (규칙이 그 조건 없이는 거부).
- 날짜는 `"YYYY-MM-DD"`(KST 달력), 시각은 `"HH:mm"`, 일시는 ISO 문자열로 저장한다.
- 영업시간 `null` = 미확인(자동 배정 제외), `[]` = 휴무. 좌표 `null` = 미확인(경로 계산 제외).
- 코스에 담을 때 `VisitItem.snapshot`에 이름·위치·영업정보·원본 `updatedAt` 사본을 남긴다. 재열람 시 최신 정보와 비교해 변경·취소를 안내하고, 사용자 확인 없이 일정을 바꾸지 않는다.
- 관리자 지정: Firebase 콘솔 또는 CLI로 `admins/{uid}` 문서를 만든다.

#### Storage 경로

- `content/{kind}/{contentId}/{file}`: 운영 콘텐츠 사진. 공개 읽기, 관리자 쓰기 (이미지·10MB 미만)
- `users/{uid}/{...}`: 개인 업로드. 본인만
